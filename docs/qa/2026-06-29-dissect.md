## Nota de escopo (honestidade)

O pedido era QA do **fracta.pro** (landing + scanner web passivo). Esse produto está
**specado e planejado, mas ainda NÃO construído**: `@fracta/web-scan` é um scaffold vazio
(`export {}`), e não existe app web para pilotar via Playwright (estávamos na Task 2 do
plano). Portanto **não há landing/scanner web para testar** — isso é um gap de estado, não
um bug.

O que existe e foi pilotado de ponta a ponta como um usuário real faria é o **produto atual:
o CLI/MCP scanner DAST** (`fracta scan --target ...`). Todos os achados abaixo vêm de
execuções reais e reproduzíveis dele. Quando o `@fracta/web-scan` for implementado, ele
herdará o `runCommand`/orquestrador — então o 🔴 abaixo é **bloqueante para o fracta.pro
também**.

## Achados (priorizados)

### [🔴 CRÍTICO] Ferramenta externa ausente vira ✅ PASSOU silencioso (gitleaks no-op no Windows)

- **Dimensão:** dados desonestos / detecção (quebra da garantia-mãe do produto)
- **Rota:** `fracta scan` → `SECRETS Agent` → `defaultGitleaksScan` → `runCommand`
- **Reproduzir:**
  1. Máquina Windows **sem `gitleaks` no PATH** (o estado default — o README manda só
     `pnpm install`, não instala gitleaks).
  2. Repo com segredo commitado e **sem `.gitignore`** (ex.: `settings.py` com
     `GITHUB_TOKEN = "ghp_..."`).
  3. `fracta scan --target <repo>` (apenas `SECRETS Agent`).
  4. Resultado observado: **`✅ PASSOU` · Critical 0 · High 0** — só um "Low: Sem
     .env.example". Nenhum aviso de que o scan de segredos **não rodou**.
- **Evidência:**
  - `which gitleaks` → não instalado.
  - `runCommand('gitleaks', ['version'])` no Windows **resolve com `code=1`** e
    `stderr="'gitleaks' não é reconhecido..."` — **não rejeita com ENOENT**.
  - Relatório real (`qa-secrets-*.md`): `Status: ✅ PASSOU`, total 1 (só higiene).
- **Causa-raiz (dupla):**
  1. `runCommand` usa `shell: process.platform === 'win32'` ([exec.ts](../../packages/core/src/exec.ts#L33)).
     Com `shell:true`, binário inexistente **não** emite `'error'`/ENOENT — o cmd.exe
     resolve com exit code. Logo o branch `if (e.code === 'ENOENT') throw new SkippedCheck`
     em [agents/secrets/src/index.ts](../../packages/agents/secrets/src/index.ts) e em
     [agents/dependencies/src/index.ts](../../packages/agents/dependencies/src/index.ts)
     é **código morto no Windows**.
  2. `defaultGitleaksScan` trata `code === 1 && relatório ausente` como **"limpo" (`return []`)**.
     Mas no gitleaks `code 1` = **"vazamentos ENCONTRADOS"** e **sempre grava relatório** —
     "code 1 + sem relatório" é uma contradição que deveria virar erro/skip, **nunca** "limpo".
- **Por que é crítico:** o pitch central do Fracta é *"audita sobre ferramentas confiáveis e
  nunca mente; ausência de achado nunca significa seguro"*. Aqui um usuário Windows recém-
  instalado escaneia um repo cheio de segredos e recebe **verde**. Quebra a garantia de
  honestidade e a capability principal de uma só vez.
- **Sugestão de fix:**
  - Pré-resolver o binário antes de rodar (ex.: `where gitleaks`/`which`), e se ausente →
    `SkippedCheck` honesto (já existe o caminho de "checks que não rodaram").
  - Em `defaultGitleaksScan`: `code === 1` **com relatório ausente** → lançar erro (status
    `error`, visível), não `return []`. Só `code === 0` + relatório ausente = "limpo".
  - Idem para `npm`/qualquer agente sobre binário externo (detectar "command not
    recognized" quando `shell:true`).
  - Bônus: preflight no boot do CLI que avisa quais ferramentas externas estão ausentes.

### [🟡 MÉDIO] Comando inválido/digitado errado escaneia TODOS os alvos (bypass do blast-radius)

- **Dimensão:** segurança de superfície / blast radius (viola regra-mãe declarada)
- **Rota:** `packages/cli/src/index.ts` — `const command = positionals[0] ?? 'scan'`
- **Reproduzir:**
  1. `fracta scna --target x` (typo "scna") ou `fracta comando-invalido --config targets.yaml`.
  2. Como `command !== 'scan'`, o guard `if (command === 'scan' && !values.target)` **não
     dispara** → segue sem `--target` → `targets` fica com **todos** os alvos do arquivo.
  3. Observado: `comando-invalido` escaneou `qa-passive` **e** `qa-repo` numa só execução.
- **Evidência:** saída com dois blocos de scan (`qa-passive — FAILED` + `qa-repo — ...`)
  numa invocação sem `--target`.
- **Por que importa:** o Fracta promete *"audita UM SaaS por vez (blast radius contido)"*.
  Um typo no nome do comando varre toda a frota de alvos — exatamente o que a regra evita.
- **Sugestão de fix:** validar `command ∈ {scan, docs, help}`; qualquer outro → erro +
  `exit(1)`. (E aplicar a obrigatoriedade de `--target` também ao comando `docs` se fizer sentido.)

### [🟡 MÉDIO] Repo com `.env` commitado e SEM `.gitignore` não é flagado

- **Dimensão:** detecção / gap de cobertura
- **Rota:** `SECRETS Agent.hygieneFindings` ([agents/secrets/src/index.ts](../../packages/agents/secrets/src/index.ts))
- **Reproduzir:**
  1. Repo com `.env` commitado **e nenhum `.gitignore`**.
  2. O check "Arquivos .env não ignorados" só roda dentro de `if (gitignore !== null && ...)`.
  3. Sem `.gitignore`, `readFileSafe` → `null` → o bloco inteiro é **pulado** → nada flagado.
- **Por que importa:** a config **mais perigosa** (sem `.gitignore` algum + `.env` versionado)
  é silenciosamente ignorada, enquanto a menos perigosa (gitignore existe mas não cobre `.env`)
  é flagada. Lógica invertida na pior ponta.
- **Sugestão de fix:** quando `.gitignore` ausente **e** existir `.env`/`.env.*` versionado,
  emitir finding `high` ("sem .gitignore e .env versionado"). Hoje depende 100% do gitleaks
  (que está quebrado no Windows — ver 🔴).

### [🟡 MÉDIO] `DEPENDENCIES Agent` compartilha o branch ENOENT morto

- **Dimensão:** detecção (latente)
- **Rota:** `agents/dependencies/src/index.ts` (`if (e.code === 'ENOENT')`)
- **Detalhe:** mesma causa do 🔴 — sob `shell:true` no Windows, `npm` ausente não rejeitaria
  com ENOENT, então o skip honesto não dispararia. Hoje mitigado porque (a) npm quase sempre
  existe e (b) há um precheck de lockfile que pulou o agente no QA ("sem package-lock.json").
  Ainda assim o tratamento de "ferramenta ausente" está incorreto e deve ser unificado com o fix do 🔴.

### [🧭 UX] Conselho de correção é cego ao stack (sempre "Exemplo NestJS")

- **Dimensão:** fricção / confiança
- **Evidência:** alvo com `stack: [nextjs]` (e até `example.com`, que não é NestJS) recebeu
  em **todos** os findings de header: *"Exemplo NestJS: `app.use(helmet())`"*. Um usuário
  Next.js/Django/Go recebe código NestJS irrelevante.
- **Sugestão:** derivar o snippet do `target.stack` (Next.js → `next.config.js headers()`,
  Express → `helmet()`, etc.) ou usar texto neutro quando o stack não for conhecido.

### [🧭 UX] Snippet de fix inventado: `helmet({ serverInfo: false })`

- **Dimensão:** correção tecnicamente errada
- **Evidência:** finding "Header proibido presente: server" sugere
  `app.use(helmet({ serverInfo: false }))`. **Helmet não tem a opção `serverInfo`.** Remover
  o header `server` (quando é da origem) se faz com `app.disable('x-powered-by')` /
  `res.removeHeader('Server')` / config do proxy.
- **Nota adicional:** no caso real o `server: cloudflare` vem do **Cloudflare**, não da
  origem — o usuário não consegue removê-lo. Vale rebaixar/contextualizar quando o header
  é de CDN conhecida.

### [🔒 SEGURANÇA-DA-FERRAMENTA] `runCommand` com `shell:true` + args concatenados

- **Dimensão:** segurança de superfície do próprio Fracta
- **Evidência:** Node emite `DEP0190 DeprecationWarning: Passing args to a child process
  with shell option true ... arguments are not escaped, only concatenated`. `repoPath` (e
  paths de config) fluem para `spawn(..., {shell:true})`.
- **Risco:** baixo hoje (paths vêm de config local do próprio usuário), mas é um vetor de
  **command injection** se um `repoPath`/host vier de fonte não confiável — relevante quando
  o `@fracta/web-scan`/fracta.pro receber input de terceiros.
- **Sugestão:** evitar `shell:true`; resolver o caminho do `.cmd` no Windows (ex.: `which`)
  e passar args como array sem shell, ou sanitizar rigorosamente.

## Cobertura e limites

- **Jornadas cobertas:** `fracta help`; caminhos de erro (sem target, target inexistente,
  config inexistente, comando inválido); scan passivo real (`example.com` → HEADERS); scan
  de repo (secrets/compliance/docs/auth/idor/tenant/race/stack/deps); scan de segredos com
  entropia realista; `pnpm test` (41/41 verdes).
- **Áreas NÃO cobertas:**
  - **fracta.pro landing + `@fracta/web-scan`** — não existem ainda (scaffold vazio).
  - **Agentes ativos** (AUTH rate-limit, IDOR, TENANT, RACE, STRIPE) com alvo autenticado —
    exigiriam um SaaS de staging com credenciais; não exercitados (ficaram `skipped`,
    corretamente reportados).
  - **MCP server** (`@fracta/mcp-server`) — não pilotado como cliente MCP nesta rodada.
  - **Caminho LLM (`--llm`)** — não acionado (opt-in, consome tokens).
  - **gitleaks de verdade** — binário ausente na máquina; por isso o 🔴 foi caracterizado
    pela ausência, não por um falso-negativo de regra do gitleaks.
- **Ações bloqueadas pelo Guard:** nenhuma destrutiva tentada — tudo read-only/local
  (scan passivo de `example.com` + repos de teste descartáveis no scratchpad).
